# Soldier — bilan des tests du 14 octobre 2026

> Archive avant corrections. Les résultats ci-dessous décrivent l’état initial, pas la version locale corrigée. Voir le [bilan après corrections](CORRECTIONS_2026-10-14.md) pour l’état actuel et les nouvelles preuves.

## Verdict

**La version locale n’est pas prête à être considérée comme sûre et stable.** Des défauts d’autorisation donnent accès à des secrets non partagés et maintiennent l’accès d’anciens membres de famille. D’autres défauts provoquent des erreurs 500, des pertes de contenu et des blocages de connexion.

**200 scénarios exécutés : 155 réussis, 39 échecs d’assertion et 6 erreurs.** Les 45 scénarios non réussis ne représentent pas 45 bugs distincts : certains vérifient plusieurs manifestations d’une même cause. Ce bilan n’est ni un pourcentage de couverture du code, ni une certification de sécurité.

Les 11 tests présents au début de cette intervention réussissaient. **189 scénarios supplémentaires** ont été ajoutés : 170 côté PHP et 19 dans un navigateur. Les échecs restent visibles dans les suites ; aucun n’a été ignoré pour rendre le bilan vert.

Périmètre : application située dans `Soldier/` à l’intérieur du dépôt, état de travail local comprenant les changements non commités, base Git `6addcb9`. Le code exécuté ne correspond donc pas au seul commit. Environnement : PHP 8.5.3, Laravel 13.30.1, Node 25.8.1 ; interface testée avec Chrome installé, piloté sans fenêtre et avec un profil temporaire.

Cette intervention ajoute des tests et de la documentation. Elle ne corrige pas le code métier, ne déploie rien et ne modifie aucune base de production.

## Méthode et limites à connaître avant de lire les résultats

- Les tests serveur utilisent SQLite **en mémoire**, des utilisateurs et des secrets fictifs. Le socle des nouveaux tests refuse une base persistante ou un environnement autre que `testing`.
- Les messages et notifications sont simulés. Les appels HTTP Laravel inattendus sont interdits. Les événements d’abonnement sont synthétiques ; aucun paiement ni envoi de courriel réel n’a été effectué.
- AES, Argon2id et les enveloppes RSA sont réellement exécutés dans les tests de coffre, de clés et de partage. Ils ne sont pas remplacés par une cryptographie factice.
- **Deux niveaux de schéma sont volontairement séparés.** `SchemaContractTest` utilise uniquement les migrations livrées. Les autres nouveaux tests fonctionnels héritent de `LegacySchemaAuditTestCase`, qui ajoute temporairement les champs manquants dans la base en mémoire pour explorer les bugs suivants. Ce complément n’est pas une migration et ne répare pas l’installation. Les succès de ces parcours sont donc conditionnels à ce schéma de diagnostic.
- Les tests navigateur importent les véritables modules TypeScript dans une page locale minimale. Ils exercent leurs comportements et manipulations du DOM, pas un parcours complet dans toutes les pages Blade. Les requêtes vers d’autres origines sont bloquées ; presse-papier et authentificateur sont simulés pour les tests concernés.
- L’inventaire contient 83 routes. Un test parcourt les **55 routes déclarant une authentification** pour vérifier leur refus des visiteurs. Cela n’équivaut pas à tester chaque combinaison d’entrée de chaque route.
- Aucun moteur de mesure de couverture PHP n’a été utilisé. Il serait inexact d’annoncer « 100 % testé ».

## Défauts prioritaires confirmés

P1 signifie ici : corriger en priorité avant une nouvelle mise en production. P2 : défaut important de fiabilité, d’intégration ou de défense supplémentaire. P3 : défaut plus localisé. Ces priorités ne sont pas des scores CVSS.

### P1 — autorisations, accès et conservation des secrets

**A01 — Un partage limité ne limite pas l’accès direct à un élément.**

Le destinataire d’un partage de l’élément A peut ouvrir l’URL de B dans le même coffre et lire son secret. Avec un partage en écriture, il peut aussi modifier B. Le test utilise un vrai secret chiffré et vérifie le contenu obtenu, pas seulement un statut HTTP.

- Cause : `app/Policies/ElementCoffrePolicy.php:10` et `:18` vérifient le coffre, le statut et la permission, mais pas `element_ids`.
- Preuves : `SharingAuthorizationTest::test_selected_share_cannot_read_an_unselected_secret_by_url` et `test_selected_share_cannot_modify_an_unselected_secret`.
- Attendu : même décision d’autorisation par élément pour lecture, édition, suppression et favoris ; filtrer une liste à l’écran ne suffit pas.

**A02 — Retirer un membre de famille ne révoque pas son accès au coffre.**

Le retrait par le propriétaire, le départ volontaire et les événements d’abonnement annulé/impayé suppriment l’adhésion, mais conservent le partage actif. L’ancien membre reste autorisé sur le coffre.

- Causes : `app/Http/Controllers/FamilleController.php:207`, `:224` et `app/Listeners/StripeEventListener.php:48`.
- Preuves : les tests `removing_member`, `leaving_family` et les deux variantes de `subscription_loss` dans `FamilyBillingTest`.
- Attendu : une opération cohérente de révocation des droits associés. Une révocation ne peut évidemment pas effacer un secret déjà copié par son ancien destinataire ; les tests portent sur les accès futurs accordés par le serveur.

**A03 — La sélection vide d’un partage est interprétée comme le coffre entier dans l’API.**

`element_ids = []` renvoie tous les éléments alors que `null` devrait être la seule représentation explicite d’un partage intégral. Le contrôleur utilise un test de vérité plutôt qu’une distinction `null`/tableau.

- Cause : `app/Http/Controllers/Api/ServicesApiController.php:48`.
- Preuve : `SharingAuthorizationTest::test_empty_share_selection_is_not_treated_as_the_entire_vault_by_api`.
- Limite : test direct du contrôleur, car l’erreur de middleware A05 bloque actuellement cette route HTTP. Il s’agit d’un défaut latent à corriger avant de la débloquer.

**A04 — Les migrations livrées ne permettent pas de reconstruire le schéma attendu.**

Il manque `users.deleted_at`, `users.is_admin`, la table `activity_logs` et les colonnes Sanctum dans `personal_access_tokens`. Cette dernière migration ne crée que l’identifiant et les dates. Le modèle utilisateur utilise pourtant `SoftDeletes` : recharger un utilisateur sur une installation neuve provoque une erreur SQL sur `deleted_at`. L’échec du journal est absorbé par son service, ce qui masque l’absence d’enregistrement.

- Sources : `app/Models/User.php:21`, `database/migrations/0001_01_01_000000_create_users_table.php`, `database/migrations/2026_03_24_002739_create_personal_access_tokens_table.php` et `app/Services/Logs/ActivityLogService.php`.
- Preuves : `SchemaContractTest` — 7 scénarios non réussis.
- Conséquence : les tests d’inscription existants peuvent réussir sur la requête de création, sans prouver que la requête suivante pourra recharger l’utilisateur. C’est une cause locale reproductible de panne après inscription, **pas une confirmation de l’état du serveur distant**.
- Attendu : migrations versionnées, compatibles avec une base neuve et avec une base historique déjà partiellement modifiée ; tests des deux chemins.

**A05 — Deux routes de l’extension échouent avant d’exécuter leur logique.**

`/api/services` et `/api/auth/oauth-data` demandent `abilities:read:services`, mais l’alias `abilities` n’est pas enregistré. Résultat : `Target class [abilities] does not exist.`, avec ou sans la permission dans le jeton.

- Sources : `routes/api.php:16` et `bootstrap/app.php:22`.
- Preuves : les quatre variantes de permission dans `ApiExtensionTest`, plus l’inventaire des routes de `HttpSurfaceTest`.
- Attendu : déclarer le middleware puis revérifier les refus de permission et les sélections de partage ; le simple retour d’un HTTP 200 ne suffira pas.

**A06 — Certaines créations et modifications perdent des données.**

- Les contenus `note` et `autre` sont absents après création par HTTP : `contenu` ne fait pas partie des données validées.
- Les champs personnels ne sont pas conservés : même problème pour `champs_personnels`.
- Renommer un élément SSH sans ressaisir sa passphrase efface celle-ci : le payload stocke `mot_de_passe`, mais sa reconstruction attend `passphrase_ssh`.
- Sources : `app/Http/Requests/StoreElementRequest.php:14` ; `app/Services/Coffre/CoffreService.php:83` et `:183`.
- Preuves : `VaultWorkflowTest`, variantes `note`/`other`, `test_custom_fields_survive_http_validation`, `test_editing_ssh_label_preserves_passphrase`.
- Attendu : contrat de données unique par type, conservation contrôlée des secrets non ressaisis, tests de lecture après chaque sauvegarde.

**A07 — La suppression est définitive malgré la promesse de corbeille.**

Le contrôleur appelle `supprimerDefinitivement()`, alors que l’interface annonce une mise en corbeille et, sur la fiche, une conservation de 30 jours. Le test constate que l’enregistrement n’existe même plus avec les éléments supprimés logiquement.

- Sources : `app/Http/Controllers/DashboardController.php:201` ; `resources/js/pages/afficher.ts:43`.
- Preuve : `VaultWorkflowTest::test_delete_retains_the_item_for_the_trash_promised_by_the_ui`.
- Attendu : implémenter réellement la corbeille/restauration/purge, ou modifier explicitement la promesse du produit avant toute suppression définitive.

**A08 — Le générateur surestime fortement la robustesse des passphrases.**

Le dictionnaire contient **100 mots**, mais le calcul utilise **7 776**. Pour cinq mots, l’interface affiche **65 bits**, contre environ **33 bits théoriques** pour le dictionnaire réel, avant prise en compte des biais de tirage. Le mode chiffres sans `0` et `1` affiche également 66 bits pour 20 caractères au lieu de 60.

- Source : `resources/js/pages/generateur.ts:3` et `:70`.
- Preuves navigateur : `displayed passphrase entropy matches the real dictionary` et `digit entropy accounts for excluded ambiguous digits`.
- Attendu : dimensionner le dictionnaire et calculer sur l’alphabet réellement utilisé. Le tirage par modulo mérite aussi un contrôle séparé de distribution ; ce bilan ne prétend pas l’avoir mesuré statistiquement.

## Ce qui fonctionne dans les conditions testées

- Inscription classique : utilisateur, clés et coffre créés ; rollback transactionnel en cas de panne cryptographique ; échec de notification absorbé.
- Chiffrement de données Unicode/binaires, contrôle des altérations du ciphertext, de l’IV, du tag et de la clé ; refus des tailles de clés et paramètres KDF invalides ; prise en compte du coût KDF persistant.
- Changement du master password conservant la KEK, la clé privée et les données ; ancien master password refusé ensuite.
- Refus des mauvais identifiants, limitation de tentatives, déconnexion nettoyant les clés et les états MFA.
- Codes MFA email hachés, expirables, à usage unique et bloqués après cinq erreurs ; configuration TOTP et QR produit localement.
- Partage par invitation : jeton haché, acceptation unique, révocation directe ; refus d’éléments d’un autre coffre ; permissions et expiration dans la matrice testée.
- Passage vers l’extension par code à usage unique et expirant ; rejet d’une redirection non autorisée et des codes invalides ; API bloquée pour les comptes MFA avant validation.
- Passkeys : challenges aléatoires, options de vérification utilisateur, exclusions, refus des données malformées et des identifiants inconnus, suppression limitée au propriétaire ; encodage navigateur de la réponse.
- Vérification d’email signée et expiration du lien ; refus CSRF testé en désactivant expressément l’exemption propre aux tests ; en-têtes no-store et HSTS dans les cas contrôlés.
- Téléversement/remplacement/suppression d’avatar, rejet d’un fichier non image, révocation d’une session limitée à son propriétaire.
- Proxy favicon mis en cache et échec réseau maîtrisé ; douze classes de courriel rendues avec échappement du nom utilisateur ; notifications et dialogues testés contre l’injection HTML.
- Génération de mots de passe selon les options testées, recherche et filtre favoris, annulation de suppression, génération dans les formulaires.

Ces succès restent soumis aux réserves du schéma de diagnostic et du périmètre navigateur décrites plus haut.

## Travail restant pour une validation complète

1. Corriger les droits de partage/révocation, les pertes de données et le schéma ; relancer les tests sans neutraliser les assertions.
2. Une fois les migrations livrées, retirer le complément de schéma du socle de diagnostic et exécuter tous les parcours sur une installation neuve réelle et sur une copie anonymisée d’une ancienne base.
3. Vérifier Google et GitHub avec des comptes de test, leurs retours exacts et leurs URI configurées ; vérifier SMTP et Stripe en environnement de test, avec signatures, reprises et idempotence.
4. Ajouter un parcours WebAuthn valide de bout en bout, avec authentificateur virtuel puis matériel : attestation/assertion, origine, RP ID, challenge consommé, compteur et rejeu. Les seuls refus de données invalides ne valident pas ce parcours.
5. Ajouter des tests complets dans les véritables pages : inscription → vérification email → connexion/MFA → coffre → partage/révocation, sur ordinateur et mobile, puis contrôler l’accessibilité.
6. Ajouter les contrôles de concurrence : consommation simultanée des codes, invitations et MFA ; double soumission ; mises à jour simultanées d’un secret et révocation pendant une lecture.
7. Vérifier l’extension elle-même si son code est fourni, les tâches planifiées/purges, les opérations administrateur mutantes et leurs limites, les volumes importants, sauvegardes et restauration. Le rendu des pages admin n’est pas une validation de toutes les actions administrateur.
8. Contrôler séparément la production : configuration effective, permissions, TLS/proxy, pilotes de session/cache, workers, journaux, secrets et ressources. Aucun de ces points ne doit être déclaré validé à partir du seul poste local.

### Direction de correction respectant SOLID

Sans modifier ces composants pendant cet audit, les responsabilités à isoler sont : une politique d’accès par élément commune au web et à l’API ; un service de révocation familiale transactionnel ; des contrats de données par type de secret ; un service de transition des états d’authentification/MFA indépendant de l’envoi des notifications ; un calculateur de robustesse alimenté par le véritable générateur. Les tests doivent vérifier les comportements observables de ces contrats. Ajouter des interfaces sans corriger les décisions d’accès ou les transactions ne suffirait pas à assurer SOLID ni la sécurité.
